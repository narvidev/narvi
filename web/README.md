# web

Narvi's web UI (§12.1): a Vite + React + TanStack Query/Router SPA. No SSR,
no BFF — the built static bundle is embedded into the control-plane binary
via `go:embed` (`internal/adapters/inbound/webui`) and served on the same
port as the REST/WS API (`narvi serve`).

Step 79 shipped the bootstrap only (toolchain, embed/serve wiring,
light/dark theming, CI); Step 80 adds the data layer (`src/api/`, `src/ws/`
— see "Data layer" below). Neither ships views — those land in the Steps
that follow, built to the same mockups.

## Layout

```
web/
  index.html                        entry HTML; inline pre-paint theme script (see below)
  vite.config.ts                    build config -- outDir points at the Go embed target, not web/dist
  vitest.config.ts                  test runner config for src/**/__tests__ (separate from vite.config.ts)
  tsconfig.vitest.json              standalone typecheck project for __tests__ trees (Node globals, DOM lib)
  src/
    main.tsx                        React root: QueryClientProvider + RouterProvider
    routes/                         TanStack Router file-based routes (__root.tsx = app shell)
    routeTree.gen.ts                gitignored -- regenerated by `npm run generate-routes`/`vite dev`/`vite build`
    components/                     shared components (e.g. ThemeToggle)
    lib/                            non-component modules (e.g. theme.ts)
    api/                            typed REST client (http.ts, endpoints.ts, queryKeys.ts) -- see "Data layer"
    ws/                             WS transport -> event log -> reducer -> query invalidation -- see "Data layer"
    styles/
      tokens.css                    design tokens extracted verbatim from docs/design/mockups.html
      base.css                      resets + the small set of generic primitives this bootstrap needs
  scripts/
    check-no-dto-redeclaration.mjs  §12.1 guard: no hand-written type reuses a contracts/gen/ts name
```

`contracts/gen/ts/*.ts` (generated from `/contracts`, §6) is this app's only
source of API response/event types — §12.1: "no hand-written response types
anywhere." `check-no-dto-redeclaration.mjs` enforces the name-collision half
of that mechanically; see its own top comment for what it checks and why.

## Commands

```
npm ci                  # install (also required before any command below)
npm run dev              # vite dev server
npm run generate-routes  # regenerate src/routeTree.gen.ts from src/routes/**
npm run typecheck        # tsc -b (regenerates routes first)
npm run lint              # oxlint
npm run check-dto-types   # the generated-DTO-name guard above
npm run typecheck:tests   # tsc -p tsconfig.vitest.json --noEmit -- typechecks src/**/__tests__
npm test                  # typecheck:tests + vitest run -- the data layer's own pipeline tests
npm run build             # typecheck + vite build -> internal/adapters/inbound/webui/dist/
```

Or, from the repo root: `make web-typecheck`, `make web-lint`,
`make web-check-dto-types`, `make web-test`, `make web-build`, `make
web-check` (all five, local convenience only — CI runs the npm scripts
directly as separate steps).

## Theming

Light/dark via CSS custom properties (`src/styles/tokens.css`), following
`prefers-color-scheme` by default, with an explicit `System`/`Light`/`Dark`
toggle (`src/components/ThemeToggle.tsx`, `src/lib/theme.ts`) that overrides
it in both directions by setting `data-theme` on `<html>`. `index.html`
carries a small inline pre-paint script that applies a stored explicit
preference before the first paint, so a reload never flashes the wrong
theme while the JS bundle loads; `src/lib/theme.ts`'s `initTheme()` re-runs
the same logic once React mounts, for the one path where JS is the first
thing to run at all (a hard-reloaded client-side route). Both places read
the same `localStorage` key (`'narvi:theme'`) by construction, kept in sync
by hand since an inline `<script>` cannot import a TS constant — see
`theme.ts`'s own comment.

## The go:embed build

`internal/adapters/inbound/webui` embeds this package's build output via a
build tag (`web_assets`), not unconditionally — a checkout that has never
run `npm run build`/`make web-build` still needs `go build ./...` to
succeed. See that package's own doc comment for the full reasoning, and
`vite.config.ts`'s own comment for why `outDir` points directly at
`internal/adapters/inbound/webui/dist` instead of the more conventional
`web/dist` (go:embed's directive syntax forbids the `..` upward traversal a
`web/dist` target would need).

## Data layer (§12.1, Step 80)

`src/api/` (typed REST client) and `src/ws/` (the WS pipeline) are this
Step's own scope. No views consume either yet (Steps 81+ do); this Step's
job is making the layer itself real, correct, and tested.

### Typed API client: generated vs. derived

§12.1 requires "no hand-written response types anywhere" and calls the
data layer a codegen output. Two shapes were available: extend
`contracts/`'s own generator (`contracts/scripts/generate-ts.mjs`) to also
emit a full REST *client* (routes, methods, request/response bindings), or
write a thin, hand-written client wrapper in `web/` whose every
request/response TYPE PARAMETER still comes from `contracts/gen/ts/
rest-dtos.ts`, never from a locally-declared interface.

This Step chose the thin wrapper (`src/api/http.ts`'s generic `request<T>`
+ `src/api/endpoints.ts`'s typed functions), because `contracts/rest/v1/
dtos.schema.json` — read directly, not assumed — models DATA SHAPES only:
`Session`, `CreateSessionRequest`, `WSTokenResponse`, … with **no path,
method, or operationId anywhere in the schema**. There is nothing for a
generator to turn into a route binding; extending the generator to emit
one would mean first inventing a whole new contracts schema surface (an
OpenAPI-shaped route manifest) this Step has no mandate to design, and
`contracts/rest/v1/dtos.schema.json`'s own top-level description is
explicit that even its DATA coverage is deliberately partial ("only
sessions, events, artifacts, ws-token, and automations … Secrets/
environments/uploads DTOs are still deliberately NOT modeled here"). A
thin wrapper needs no such upfront design: every endpoint `src/api/
endpoints.ts` adds is a 3-line function whose request/response types are
whatever `rest-dtos.ts` already generates, so §12.1's own rule ("no
hand-written response types") holds by construction — there is no
interface in `src/api/` for `check-no-dto-redeclaration.mjs` to ever need
to flag, because there is nothing to redeclare.

### `contracts/gen/ts` via `@narvi/contracts`, not a relative path

`contracts/` is its own standalone npm project (`contracts/package.json`'s
own description: "does not make the repo root an npm project; phase 6
brings its own frontend package"), not an npm workspace dependency of
`web/`. `vite.config.ts` and `tsconfig.app.json` both alias
`@narvi/contracts` to `../contracts/gen/ts` (mirrored in
`vitest.config.ts`/`tsconfig.vitest.json` for tests), so every generated
file is imported as `@narvi/contracts/rest-dtos`, `@narvi/contracts/
client-ws`, etc. — one stable specifier every future Step can use, rather
than a relative `../../../contracts/gen/ts/...` path whose `../` count
silently breaks (wrong file, not a compile error) if the importing file
ever moves.

### The WS pipeline: transport → event log → reducer → query invalidation

`src/ws/transport.ts` (`ClientWsTransport`) owns the raw WS connection to
`GET /sessions/{sessionID}/ws?type=client` (§6.2) and reconnects with
backoff; `src/ws/eventLog.ts` (`EventLog`) is the append-only, deduplicated,
id-ordered event store; `src/ws/reducer.ts` folds that log into
`SessionActivityState`; `src/ws/invalidation.ts` maps a newly-folded
event's own `type` to the TanStack Query keys (`src/api/queryKeys.ts`)
that just went stale. `src/ws/sessionStream.ts` (`SessionStream`) composes
all four into one object per viewed session — see its own top comment for
how a live broadcast is turned into a `fetch_history` round-trip rather
than trusted as log data (next section).

### Redelivery

The sandbox↔control-plane protocol (§9.3) resends unacked critical frames
on reconnect, deduped server-side on `(session_id, message_id)`. Reading
`contracts/client-ws/v1/protocol.schema.json` and the Go server that
implements it (`internal/adapters/inbound/wshub/client.go`) directly (not
assumed) shows the client-facing stream has a DIFFERENT, but still real,
redelivery property:

- Every `subscribe` (initial connect **and every reconnect**) replies with
  a fresh `SubscribedPayload` whose `events` field is the session's own
  OLDEST up to 200 events (`client.go`'s own `initialReplayLimit`,
  `events.ListForSession(ctx, sessionID, 0, initialReplayLimit)` —
  `afterID=0`, unconditionally, every time). A client that reconnects
  after having already processed those same events receives them again,
  verbatim, with their real `id`.
- `client.go`'s own `eventWireMap` doc comment says this directly: `id`
  exists on this wire shape "for client-side de-dup against live
  broadcasts" — i.e. the dedup requirement is a documented, intentional
  property of this protocol, not an inference.
- `EventLog.append`/`appendMany` (`src/ws/eventLog.ts`) is that dedup,
  keyed on `id`. `sessionStream.test.ts`'s own "redelivered replay" test
  drives a real reconnect through a real fake server and asserts a
  redelivered event is applied exactly once; this Step's own PR
  description names the mutation test proving that guard is load-bearing
  (removing it makes that test, and `eventLog.test.ts`'s own dedup tests,
  fail).

A separate, narrower case exists on the LIVE broadcast path: a broadcast
frame is `internal/app/ports/eventbroadcaster.go`'s own "exact raw stored
payload bytes… no separate wrapper envelope" — confirmed by reading
`internal/app/sessionactor/actor.go`'s `appendEvent`/`appendRawEvent`
directly: `a.pendingBroadcast` holds the SAME bytes written to the
`payload` column, nothing else — **no `id`, and generally no `type`
either**. There is structurally no key to dedup a live broadcast frame
against an `EventEnvelope` by, so this layer does not try: `transport.ts`
hands every live broadcast to `onBroadcast` as an opaque, untrusted
wake-up signal, and `sessionStream.ts` answers it by re-running the SAME
id-bearing `fetch_history` path used for backfill, never by trying to
parse the broadcast's own bytes as log data. `internal/app/ports/
eventbroadcaster.go`'s own doc comment says this is the intended recovery
path verbatim: "any client can always recover a missed live push via
fetch_history's cursor-paginated replay."

### Reconnect gaps

`SubscribedPayload.events` is capped at 200 items AND 16KiB
(`maxInitialReplayBytes`) with **no flag in the payload** telling the
client whether truncation actually happened. This layer therefore never
guesses: `SessionStream` always runs at least one `fetch_history` backfill
pass after every subscribe (initial connect or reconnect), walking forward
from the log's own highest known id until the server itself returns
`nextCursor: null` — proof, from the server, that no gap remains as of
that round-trip. `syncState` (`idle` / `syncing` / `complete`) surfaces
this honestly: it is forced back to `syncing` the instant the connection
is anything other than `open` (a disconnect means this client can no
longer vouch for completeness), and only becomes `complete` once a real
`fetch_history` round-trip confirms it. A consumer that ignores `syncState`
can still render a confidently-wrong "N events" count; one that checks it
never has to.

### Ordering

`reduceLog` (`src/ws/reducer.ts`) assumes `events.id` is causal order
within a session. The id is a Postgres bigserial drawn from one
table-wide sequence when the row is inserted, not when it commits; what
makes it order is that within one session ids are allocated in commit
order, because every insert takes the session row lock before drawing its
id (`CreateEvent`, `internal/adapters/outbound/postgres/queries/events.sql`).
So an event never becomes visible after a higher id of the same session
has, which is also what lets a backfill ask only for ids above the
highest one it holds without skipping any. `reduceLog` folds strictly in
id order — never in network
arrival order. This is safe because `EventLog.entries()` is always
id-sorted by construction (`eventLog.ts`'s own `lowerBound`-based sorted
insertion), regardless of the order `appendMany` was called in — which
matters because it is NOT always call order: a reconnect's fresh replay,
an in-flight backfill page, and a live-broadcast-triggered backfill page
are independent round-trips that can resolve in any relative order.
`reducer.test.ts`'s own ordering test proves `reduceLog` produces a
DIFFERENT (and wrong) result if fed the same two events in arrival order
instead of id order — pinning that the id-sort step is load-bearing, not
redundant.

### What never reaches this layer's state

Not this Step's job to render anything, but the layer already decides what
CAN reach a future view: nothing here holds a raw secret, token, or
credential in memory beyond the single WS token `getToken()` hands to the
transport for the connection handshake itself (never stored in
`EventLog`/`SessionActivityState`/TanStack Query's own cache). The
management APIs (`contracts/rest/v1`) are write-only by design
(`ProviderCredential.maskedValue`, never the real value) — this layer
introduces no new way to leak one.

### Testing

`src/ws/__tests__/fakeServer.ts` runs a REAL local `ws`-backed WebSocket
server; `transport.test.ts` and `sessionStream.test.ts` drive the REAL
`ClientWsTransport`/`SessionStream` (using the browser-standard global
`WebSocket` client, present natively in Node 22+) against it over an
actual loopback socket — nothing about the transport or the pipeline under
test is mocked, only the server's own scripted responses are.
`eventLog.test.ts`/`reducer.test.ts`/`invalidation.test.ts` cover each
pipeline stage in isolation. `npm test` (`typecheck:tests` + `vitest run`)
runs all of it.
